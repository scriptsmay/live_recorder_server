# 日志功能开发方案

## 1. 概述

本文档为 Live Recorder Server 日志系统的扩展功能提供详细开发方案，涵盖以下功能：

| 优先级 | 功能                             | 状态       |
| ------ | -------------------------------- | ---------- |
| P1     | morgan 输出到文件 + 基础滚动切割 | **已实现** |
| P2     | 实时日志查看（SSE 简化版）       | **已实现** |
| P3     | 日志自动清理                     | **已实现** |
| P4     | 虚拟滚动（超大日志优化）         | **暂缓**   |

**设计原则**：保持轻量，避免将视频录制服务变成日志系统项目。优先解决真实运维痛点（为什么没录上、ffmpeg 报了什么、上传卡在哪）。

---

## 2. 已实现功能（P1）

### 2.1 实现内容

**morgan 日志持久化**：

- 同时输出到控制台和文件
- 日志文件路径：`logs/access.log`

**滚动切割策略**：

- 单个当前日志文件最大 10MB
- 当前日志固定写入 `access.log` / `server.log`
- 日期变更时归档为 `access.YYYY-MM-DD.log` / `server.YYYY-MM-DD.log`
- 同一天超过大小限制时归档为 `access.YYYY-MM-DD.N.log` / `server.YYYY-MM-DD.N.log`
- 每天最多保留 5 个大小备份，超过备份数时自动删除最旧文件
- 轮转模块会清理超过 30 天的同类日期归档日志

### 2.2 代码位置

- Morgan 中间件：`middleware/access-log.js`
- 应用日志系统：`lib/core/logger.js`
- 日志页面与 API：`router/logs.js`（GET `/logs`、`/api/logs/content`、`/api/logs/stream`）

### 2.3 当前能力与限制

**已有能力**：

- `access.log`：生产环境和开发环境都会写入，带日期+大小双维度轮转
- `server.log`：**仅在生产环境写入**（`NODE_ENV=production`），带日期+大小双维度轮转
- 进程日志（ffmpeg/biliup）：通过 `lib/utils/proc-log.js` 记录到 `logs/` 目录，格式 `{进程名}_{会话ID}.log`
- `/logs` 页面可读取最后 2000 行，并支持 SSE 实时查看

**待解决问题**：

- 缺少便捷的关键词过滤功能

## 3. 实时日志查看（P2 - 简化版）

### 3.1 需求分析

**功能需求**：

- 用户可在浏览器中实时查看日志更新
- 支持手动开启/关闭实时更新
- 支持自动滚动到最新内容
- **不引入复杂依赖**，复用现有 `/logs` 页面结构

**技术选型**：Server-Sent Events (SSE)

**选型理由**：

- 单向数据流，适合日志推送场景
- 自动重连机制
- 轻量级，无需额外依赖

**关键决策**：

- **不使用 `fs.watch`**：日志轮转、macOS/Linux 行为差异、文件重命名时容易漏
- **采用 offset + createReadStream**：记录文件偏移量，用 `fs.stat` + `createReadStream({ start })` 读取追加内容，更稳定可靠

### 3.2 架构设计

```
┌──────────────────┐    SSE连接    ┌──────────────────┐
│   前端浏览器      │◄─────────────►│   Express Server │
│  (EventSource)   │               │   (SSE Endpoint) │
└──────────────────┘               └─────────┬────────┘
                                             │ fs.stat +
                                             │ createReadStream
                                             ▼
                                       ┌──────────────┐
                                       │  日志文件    │
                                       └──────────────┘
```

**核心流程**：

1. 客户端建立 SSE 连接，传递 `file` 和 `tail` 参数
2. 后端读取文件末尾 N 行作为初始内容
3. 记录当前文件偏移量（offset）
4. 定时（如每 1s）检查文件大小变化，如有新内容则从 offset 位置读取并推送
5. 客户端接收新日志行并追加显示

### 3.3 API 设计

| 端点                | 方法 | 描述                              |
| ------------------- | ---- | --------------------------------- |
| `/api/logs/stream`  | GET  | 建立 SSE 连接，实时推送日志       |
| `/api/logs/content` | GET  | 获取指定日志文件内容（支持 tail） |

#### 3.3.1 GET /api/logs/stream

**请求参数**：
| 参数 | 类型 | 必填 | 描述 |
|------|------|------|------|
| file | string | 是 | 日志文件名（需白名单校验，防止路径遍历） |
| tail | number | 否 | 初始获取的行数，默认 100 |

**响应格式**：SSE 事件流

```
event: log
data: {"line": "2024-01-01 12:00:00 GET /api/test 200 5ms"}

event: log
data: {"line": "2024-01-01 12:00:01 POST /api/notify/live_download 200 10ms"}
```

**实现要点**：

- 使用 `fs.stat` 获取文件大小，对比上次记录的 offset
- 使用 `createReadStream({ start: offset, end: newSize - 1 })` 读取新增内容
- 按行分割后逐行推送 SSE 事件
- 设置合理的轮询间隔（如 1s），避免频繁 I/O
- 客户端断开时清理定时器和服务端资源

#### 3.3.2 GET /api/logs/content

**请求参数**：
| 参数 | 类型 | 必填 | 描述 |
|------|------|------|------|
| file | string | 是 | 日志文件名 |
| tail | number | 否 | 获取最后 N 行，默认 2000 |

**响应格式**：

```json
{
  "file": "access.log",
  "lines": ["line1", "line2", "..."],
  "truncated": true
}
```

**实现要点**：

- 从文件末尾反向读取，避免加载整个大文件到内存
- 不强制返回精确 `total_lines`，避免为了统计总行数而扫描整个大文件
- 可返回 `truncated` 标记，表示响应只包含文件尾部内容

### 3.4 前端设计

**改造现有 `/logs` 页面**：

- 保留左侧日志文件列表（如有）
- 右侧日志内容展示区域增加两个控件：
  - **实时开关**：开启后建立 SSE 连接，关闭后断开
  - **自动滚动开关**：新日志到来时是否自动滚动到底部
- 日志内容区域保持简单文本展示，暂不引入语法高亮（降低复杂度）

**交互逻辑**：

1. 用户选择日志文件后，默认显示最后 2000 行（调用 `/api/logs/content`）
2. 点击「实时查看」按钮，建立 SSE 连接（调用 `/api/logs/stream?file=xxx&tail=100`）
3. 新日志到达时，如自动滚动开启则滚动到底部
4. 用户关闭「实时查看」时断开 SSE 连接；关闭「自动滚动」时仍接收日志但不滚动到底部

### 3.5 开发计划

**实现状态**：已完成。`router/logs.js` 提供 `/logs` 页面、`/api/logs/content`、`/api/logs/stream` 和日志删除接口；`views/logs.ejs` 提供实时查看与自动滚动开关。

| 任务  | 描述                              | 预估工时 |
| ----- | --------------------------------- | -------- |
| 3.5.1 | 新增 `router/logs.js`             | 0.5 小时 |
| 3.5.2 | 实现 `GET /api/logs/content`      | 1 小时   |
| 3.5.3 | 实现 `GET /api/logs/stream` (SSE) | 2 小时   |
| 3.5.4 | 前端增加实时控件                  | 1.5 小时 |
| 3.5.5 | 测试与调试                        | 1 小时   |

## 4. 日志自动清理（P3）

### 4.1 需求分析

**问题背景**：

- `access.log` 虽有轮转，但备份文件会长期占用磁盘
- `server.log`（生产环境）会持续增长
- ffmpeg/biliup 进程日志（`{进程名}_{会话ID}.log`）会随录制次数累积
- 缺乏自动清理机制，可能导致磁盘空间耗尽

**功能需求**：

- 按文件修改时间清理（保留最近 N 天）
- 按总大小清理（超过阈值时删除最旧文件）
- 启动时自动执行一次，之后每日定时执行
- **简化配置**：初期使用硬编码默认值，后续再考虑 settings 表配置

**清理策略**：

- 默认保留 **30 天** 或总量 **1GB**（满足条件即触发清理）
- 优先删除最旧的文件
- 保护当前正在写入或最近仍活跃的日志文件：
  - 固定保护 `access.log`、`server.log`
  - 跳过最近几分钟内修改过的 `.log` 文件，避免误删正在写入的 ffmpeg/biliup 进程日志

### 4.2 技术方案

**实现方式**：创建 `LogCleanupService` 服务类

建议放在 `services/LogCleanupService.js`，与业务服务层保持一致；日志目录路径通过项目根目录解析，避免因文件移动导致 `../logs` 层级错误。

**核心逻辑**：

```javascript
class LogCleanupService {
  constructor() {
    this.logsDir = path.join(process.cwd(), 'logs');
    this.retentionDays = 30; // 默认保留 30 天
    this.maxTotalSize = 1 * 1024 * 1024 * 1024; // 默认 1GB
    this.activeWindowMs = 5 * 60 * 1000; // 最近 5 分钟修改过的日志视为活跃
  }

  async cleanup() {
    // 1. 扫描 logs/ 目录下所有 .log 文件
    // 2. 计算总大小，如超过 maxTotalSize 则按修改时间排序删除最旧文件
    // 3. 删除超过 retentionDays 的文件
    // 4. 记录清理日志
  }
}
```

**调度策略**：

- 应用启动时立即执行一次（`lifecycle.js` 中调用）
- 使用 `setInterval` 每日执行一次（24h = 86400000ms）
- 也可集成到现有看门狗任务中（如 `watchdog.js`）

**安全考虑**：

- 只清理 `.log` 后缀文件
- 跳过固定保护文件和最近仍活跃的日志文件
- 记录每次清理的文件列表和释放空间

### 4.3 开发计划

**实现状态**：已完成。`services/LogCleanupService.js` 在启动时执行一次清理，并由 `lib/core/lifecycle.js` 启动每日定时清理。

| 任务  | 描述                     | 预估工时 |
| ----- | ------------------------ | -------- |
| 4.3.1 | 实现 `LogCleanupService` | 2 小时   |
| 4.3.2 | 集成到启动生命周期       | 0.5 小时 |
| 4.3.3 | 测试清理逻辑             | 1 小时   |

**注意**：搜索过滤功能（关键词、正则、时间范围）**暂缓实现**。当前日志格式不统一，强行做时间/级别解析会变复杂。如需搜索，可先用浏览器自带查找功能（Ctrl+F）或后端返回全量内容后前端过滤。

## 5. 虚拟滚动优化（P4 - 暂缓）

### 5.1 决策说明

**暂缓理由**：

- 现有 `access.log` / `server.log` 单文件 10MB 轮转，进程日志也有 10MB 左右的保护
- 后端只返回 tail 或按字节分页，前端不会真的需要渲染 100MB+
- 自研虚拟滚动的维护成本不低，收益暂时不够
- 不符合「保持轻量」的设计原则

**何时重新考虑**：

- 当出现单个日志文件 >100MB 且用户反馈页面卡顿时
- 或有明确需求需要一次性加载大量历史日志时

**替代方案**：

- 限制单次加载行数（如最多 5000 行）
- 提供「加载更多」按钮，按需分页加载
- 引导用户使用关键词过滤缩小范围

## 6. 技术风险评估

| 风险点         | 描述                     | 影响           | 缓解措施                              |
| -------------- | ------------------------ | -------------- | ------------------------------------- |
| SSE 连接断开   | 网络不稳定导致连接中断   | 日志更新延迟   | SSE 自动重连 + 断线重连时获取最新内容 |
| 大文件内存占用 | 超大日志文件导致内存溢出 | 服务端崩溃     | 按行读取 + 流式处理，不一次性加载     |
| 并发连接数     | 大量客户端同时连接       | 服务器资源耗尽 | 限制并发连接数，设置连接超时          |
| 文件轮转冲突   | 日志轮转时 offset 失效   | 读取异常       | 检测文件大小突变，重置 offset         |

## 8. 安全考虑

1. **路径遍历防护**：严格校验日志文件名，禁止 `..` 等路径跳转字符，使用白名单机制
2. **访问控制**：后续可考虑添加登录验证
3. **敏感信息过滤**：日志中不应记录密码、Token 等敏感信息
4. **SSE 连接限制**：限制单个 IP 的最大 SSE 连接数，防止资源耗尽

根据评估建议，最适合本项目的执行路线如下：

### 第二阶段：日志查询 API（已完成）

1. 实现 `GET /api/logs/content?file=&tail=2000`，支持获取指定文件末尾 N 行
2. 实现文件白名单校验和路径安全校验
3. 前端调用新 API 替换原有逻辑

### 第三阶段：实时日志查看（已完成）

1. 实现 `GET /api/logs/stream?file=&tail=100`，使用 offset + createReadStream 方案
2. 前端增加两个控件：实时开关、自动滚动
3. 测试 SSE 连接稳定性、断线重连、文件轮转场景

### 第四阶段：自动清理服务（已完成）

1. 实现 `LogCleanupService` 类，支持按时间和总大小清理
2. 集成到 `lib/core/lifecycle.js`，启动时执行一次
3. 设置每日定时任务（`setInterval` 24h）
4. 测试清理逻辑，验证不会误删正在写入的文件

**总计工时**：约 9.5 小时

**不包含**：

- ❌ P4 虚拟滚动（暂缓）
- ❌ 正则搜索、时间范围搜索、日志级别过滤（暂缓）
- ❌ 复杂的 settings 配置项（初期硬编码默认值）

这样能解决真实运维痛点，又不会把一个视频录制服务变成日志系统项目。
